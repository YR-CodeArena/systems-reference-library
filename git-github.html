Comprehensive Git & GitHub Master Notes

Based on Hitesh Choudhary's (Chai aur Code) Git and GitHub Complete Course, this guide provides a structured, end-to-end breakdown of Version Control, Git internals, branching, rebasing, remote syncing with GitHub, and open-source contribution workflows.

1. Introduction: Version Control, Git vs. GitHub

What is Version Control (VCS)? [02:10]

A Version Control System (VCS) manages and records the history of changes made to files over time. Think of it like saving checkpoints in a video game [15:59]:

  • When your software reaches a stable, working state, you create a checkpoint.
  • If a newly added feature introduces bugs, you can instantly revert back to any prior checkpoint without losing your code history.
  • Multiple developers can work concurrently on the same codebase without overwriting one another's work [22:18].

History of Version Control [17:46]

Before Git became the industry standard, various proprietary and early open-source VCS solutions existed:

  • SCCS & RCS: Early revision systems.
  • CVS & SVN (Subversion): Centralized VCS systems where developers depended directly on a central server.
  • Perforce & Mercurial: Advanced commercial/open-source alternatives.
  • Git (2005): Created by Linus Torvalds for the Linux kernel development. It is Distributed (every developer possesses the full repository history locally), free, open-source, and extremely fast.

Git vs. GitHub [14:47]

CONCEPT GIT GITHUB
Nature Software / CLI tool running locally on your computer. Cloud hosting platform / Web service for Git repositories.
Primary Role Tracks file changes, creates checkpoints (commits), manages branches. Hosts remote repositories, enables collaboration, PRs, issue tracking, CI/CD.
Alternatives Mercurial, SVN GitLab, Bitbucket, Azure Repos, Gitea [02:26:13]

2. Global Setup & Initial Configuration

Installing & Verifying Git [24:26]

Check your installed version in your terminal (macOS/Linux/Git Bash on Windows):

Bash 
git --version

Configuring Author Details [30:28]

Git embeds author information inside every commit. Set this globally across your machine:

Bash 
# Set your global username
git config --global user.name "Your Name"

# Set your global email (use the email associated with GitHub)
git config --global user.email "your.email@example.com"

# View all active Git configurations
git config --list

Configuring VS Code as the Default Editor [49:15]

By default, Git opens the terminal-based Vim editor for multi-line commit messages or merge conflicts. To set VS Code as the default:

Bash 
git config --global core.editor "code --wait"

(Ensure code is added to your system PATH via VS Code: Cmd/Ctrl + Shift + P → Shell Command: Install 'code' command in PATH).

3. Core Workflow & Lifecycle Areas

3 Distinct Local Zones

Git organizes your files across three distinct local zones before pushing to a remote server [37:43]:

Architecture Diagram 
+------------------+           git add            +------------------+          git commit          +-------------------+          git push          +------------------+
| Working Directory| ---------------------------> |   Staging Area   | -----------------------------> | Local Repository  | -------------------------> | Remote (GitHub)  |
| (Modified Files) |                              |  (Index / Cache) |                                |   (.git folder)   |                            |  (Origin / Main) |
|                  | <--------------------------- |                  | <----------------------------- |                   | <------------------------- |                  |
+------------------+          git restore         +------------------+         git reset HEAD~        +-------------------+          git pull          +------------------+
  1. Working Directory: The active workspace where you create, edit, and delete files.
  2. Staging Area (Index): The preparation zone where files are staged ( git add ) for the next checkpoint [38:06].
  3. Local Repository (.git): The internal database tracking committed snapshots [38:25].
  4. Remote Repository: The remote copy hosted on platforms like GitHub [02:25:06].

The Core Rhythm: Write → Add → Commit [36:55]

1. Initialize Repository:

Bash 
git init

Creates a hidden .git folder containing metadata and object databases [34:14].

2. Check Repository Status:

Bash 
git status

3. Stage Changes:

Bash 
# Stage a specific file
git add file1.txt

# Stage multiple specific files
git add file1.txt file2.txt

# Stage all modified and untracked files
git add .

4. Unstage a Staged File: [41:32]

Bash 
git rm --cached <file-name>
# or
git restore --staged <file-name>

5. Commit Changes (Checkpoint Creation): [42:13]

Bash 
git commit -m "Add authentication middleware"

4. Commit Best Practices & Commit Logs

Atomic Commits [46:15]

Rule: A commit should represent a single logical unit of work (e.g., adding a specific UI component, fixing a single calculation bug). Do not batch weeks of unrelated tasks into one massive commit. Atomic commits make rollbacks and debugging easier.

Imperative Commit Tone [47:43]

Use present-tense imperative mood (as if issuing a command to the codebase):

  • • Add user profile endpoint (Preferred)
  • ˆ Added user profile endpoint (Avoid past tense)
  • ˆ Adds user profile endpoint (Avoid third-person)

Inspecting History with git log [44:30]

Bash 
# Detailed commit log (Shows full 40-char SHA-1 hash, author, date, and message)
git log

# Concise one-line per commit log
git log --oneline

# Graphical representation of branch history
git log --oneline --graph --all

5. .gitignore & .gitkeep

Excluding Files with .gitignore [51:19]

Store files you never want tracked (environment variables, system files, dependencies) in a root .gitignore file:

.gitignore 
# Environment variables and secrets
.env
.env.local

# Dependency folders
node_modules/
vendor/
__pycache__/

# Build directories
dist/
build/

# Operating system / IDE specific files
.DS_Store
.vscode/

Keeping Empty Directories with .gitkeep [53:33]

Git tracks files, not empty folders. If you need an empty folder tracked (e.g., logs/, uploads/), add a dummy .gitkeep file inside:

Bash 
mkdir uploads
touch uploads/.gitkeep
git add uploads/.gitkeep
git commit -m "Track uploads directory"

6. Deep Dive: Git Internals & Architecture

Git is essentially a content-addressable key-value datastore living inside the .git/ folder [58:00].

The "Three Musketeers" of Git Storage [01:00:11]

Every object stored in .git/objects/ is identified by a 40-character SHA-1 hash:

  1. Blob (Binary Large Object): [01:01:48] Stores the raw contents of a file (does not store metadata or file names).
  2. Tree Object: [01:01:35]
    • Represents a directory structure.
    • Maps file permissions, modes, and human-readable filenames to their respective Blob and Sub-Tree hashes.
  3. Commit Object: [01:01:03]
    • Stores the root Tree SHA, parent commit hash(es), author info, committer info, timestamp, and the commit message.
Git Object Graph Layout 
Commit Object Root Tree: 8a4b2c... Parent: 3f19ab... Author / Committer / Timestamp / Message
    |
    v
Tree Object 100644 blob e69de2... index.js
            100644 blob 4b825d... package.json
            040000 tree 9f82d1... src/
    |
    v
Blob Object (Raw file content of text)

Porcelain vs. Plumbing (Gardening) Commands [01:04:47]

  • Porcelain Commands: High-level, user-friendly commands developers use every day ( git add, git commit, git checkout ).
  • Plumbing / Gardening Commands: Low-level commands manipulating raw objects directly:
Bash (Plumbing Commands) 
# Inspect the content and type of any SHA-1 object
git cat-file -p <object-hash>
git cat-file -t <object-hash>

# Low-level hashing and index manipulation [01:06:47]
git hash-object -w <filename>
git update-index --add --cacheinfo 100644 <blob-sha> <filename>
git write-tree

7. Git Branching & HEAD

A branch in Git is simply a lightweight, movable pointer to a commit hash [01:13:45].

The HEAD Pointer [01:15:00]

HEAD points to the current active branch or commit you are working on. Viewable in .git/HEAD (e.g., ref: refs/heads/main).

Managing Branches [01:16:37]

Bash 
# List all local branches (* denotes active branch)
git branch

# Create a new branch
git branch feature-login

# Switch to an existing branch
git switch feature-login
# or
git checkout feature-login

# Create AND switch to a new branch in a single command [01:21:26]
git switch -c feature-login
# or
git checkout -b feature-login

# Rename a branch [01:45:37]
git branch -m <old-name> <new-name>
# e.g., git branch -m master main

# Delete a branch (safe delete prevents losing unmerged work) [01:45:47]
git branch -d feature-login

# Force delete a branch
git branch -D feature-login

8. Merging & Conflict Resolution

Merging integrates changes from one branch into another [01:23:18].

1. Fast-Forward Merge [01:27:04]

Occurs when the target branch has no new commits since the source branch branched off. Git simply moves the pointer forward.

Bash 
# Step 1: Switch to the receiving branch
git switch main

# Step 2: Merge the feature branch
git merge feature-login

2. Non-Fast-Forward (3-Way) Merge [01:27:19]

Occurs when both main and feature branches have independent new commits. Git combines histories and creates a Merge Commit [01:33:26].

3. Handling Merge Conflicts [01:34:12]

A conflict occurs when two branches modify the same line in the same file differently.

Conflict Markers Breakdown [01:36:40]

Conflict Diff Markers 
<<<<<<< HEAD (Current Branch e.g., main)
const API_URL = "https://api.production.com";
=======
const API_URL = "https://api.staging.com";
>>>>>>> bug-fix (Incoming Branch)

Steps to Resolve Conflicts [01:40:07]:

  1. Open conflicting file(s) in VS Code.
  2. Select one option (Accept Current, Accept Incoming, Accept Both, or edit manually).
  3. Ensure all marker lines ( <<<<<<< , ======= , >>>>>>> ) are completely removed.
  4. Stage the resolved files:
    Bash 
    git add <resolved-file>
  5. Finalize the merge:
    Bash 
    git commit -m "Resolve merge conflict in API configuration"
  6. (Optional) If you need to discard the merge mid-way: [01:39:26]
    Bash 
    git merge --abort

9. Inspection, Stashing & Tagging

git diff [01:48:36]

Bash 
# Compare unstaged working directory changes vs. staging area
git diff

# Compare staged changes vs. the last commit [01:49:53]
git diff --staged

# Compare differences between two commits [01:53:07]
git diff <commit-sha-1>..<commit-sha-2>

# Compare two branches
git diff main..feature-branch

git stash (Temporary Shelf) [01:53:59]

Saves dirty/uncommitted modifications onto a local stack so you can switch branches cleanly.

Bash 
# Stash current uncommitted changes
git stash

# or with a custom message
git stash save "WIP: Navbar redesign"

# List all stashed items [01:56:00]
git stash list

# Apply top stash and KEEP it in the stash list [01:56:52]
git stash apply

# Apply a specific stash entry
git stash apply stash@{1}

# Apply top stash and REMOVE it from the stash stack [01:57:17]
git stash pop

# Discard a specific stash item
git stash drop stash@{0}

# Clear all stashed changes
git stash clear

git tag (Milestones & Releases) [01:58:03]

Used to mark specific release points in history (e.g., v1.0.0).

Bash 
# Create a lightweight tag on the current commit
git tag v1.0.0

# Create an annotated tag (Recommended for releases) [01:58:27]
git tag -a v1.0.0 -m "Release version 1.0.0"

# Tag a specific past commit
git tag -a v0.9.0 <commit-sha> -m "Beta release"

# List all tags [01:59:40]
git tag

# Push a specific tag to remote GitHub repository [02:00:51]
git push origin v1.0.0

# Push all local tags to GitHub
git push origin --tags

10. git rebase vs. git merge & git reflog

git rebase Explained [02:03:50]

Instead of creating a merge commit, Rebase moves the starting point of your feature branch to the tip of the base branch, producing a linear, clean commit history [02:06:07].

Rebase Topology 
Before Rebase: D---E (feature) / A---B---C (main)
After 'git rebase main' on feature: A---B---C---D'---E' (feature linear history)
Bash 
# Step 1: Switch to the feature branch you want to rebase
git switch feature-branch

# Step 2: Rebase on top of the updated base branch [02:16:35]
git rebase main

The Golden Rule of Rebasing [02:12:44]: Never rebase a public/shared branch (like main). Only rebase local, unshared feature branches to keep history clean before merging.

git reflog & Emergency Recovery [02:18:26]

git reflog (Reference Log) records every movement of HEAD (commits, checkouts, resets, merges, rebases). Even "lost" or deleted commits can be recovered here.

Bash (Reflog Inspection) 
# Display entire HEAD movement history
git reflog

# Output example:
# 7b2c1a4 HEAD@{0}: commit: Add navbar
# 9a8f3b1 HEAD@{1}: checkout: moving from main to feature
# 3c4d5e6 HEAD@{2}: reset: moving to HEAD~1

Recovering Lost Commits with Hard Reset [02:20:41]:

Bash 
# Hard reset back to any historical point identified in reflog
git reset --hard <sha-or-HEAD@{n}>
# e.g., git reset --hard 7b2c1a4

(Caution: --hard overwrites your local working directory and staging area).

11. Connecting Local Git to GitHub (SSH & Remotes)

Setting Up SSH Keys [02:27:20]

GitHub requires SSH authentication for terminal operations:

1. Generate a new SSH Key Pair [02:29:19]:

Bash 
ssh-keygen -t ed25519 -C "your.email@example.com"

(Press Enter to accept default file location /Users/username/.ssh/id_ed25519 and set an optional passphrase).

2. Start SSH Agent & Add Key (macOS/Linux) [02:30:47]:

Bash 
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

3. Copy Public Key:

Bash 
# macOS:
pbcopy < ~/.ssh/id_ed25519.pub

# Windows (Git Bash):
clip < ~/.ssh/id_ed25519.pub

# Linux:
cat ~/.ssh/id_ed25519.pub

4. Add to GitHub [02:28:36]:

Go to GitHub → Settings → SSH and GPG Keys → New SSH Key → Paste and Save.

Linking Local Repo to GitHub & Pushing [02:35:45]

Bash 
# Check existing remotes
git remote -v

# Link local repository to remote GitHub repository as 'origin'
git remote add origin git@github.com:username/repository-name.git

# Set default upstream and push 'main' branch [02:39:59]
git push -u origin main

# Subsequent pushes on this branch can now simply be: [02:40:26]
git push

# Pull latest changes from remote repository
git pull

12. Open Source Contribution & PR Etiquette

Open Source Contribution Rules [02:44:28]

  • Talk First: Open an issue or communicate on the community Discord/Discussions before submitting code [02:45:37].
  • Add Tangible Value: Avoid low-effort, spam pull requests (e.g., changing single typos in README.md or formatting changes) [02:44:51].
  • Maintain Code Quality: Follow project linting rules, write meaningful commit messages, and document your changes [02:51:06].

End-to-End Open Source Contribution Workflow [02:47:35]

Workflow Architecture 
+--------------------+  Fork   +--------------------+ | Original Upstream | -----------------> |    Your GitHub     |
|  (Maintainer Repo) |         |  (Remote: origin)  | +--------------------+                     +--------------------+
|                    |         |                    |                                                  |
|                    |         |                    |                                                  | git clone
|                    |         |                    |                                                  v
|                    |         |                    |                                        +--------------------+
|                    |         |                    | <----------------- git push ---------  | Local Machine Repo |
|                    |         |                    |                    (Feature Branch)    | (Local Workspace)  |
|                    |         |                    |                                        +--------------------+
|                    |         |                    | -----------------------------------------> Open Pull Request (PR)
+--------------------+         +--------------------+
  1. Fork the Repository [02:47:41]: Click Fork on the top right of the upstream GitHub repository.
  2. Clone Your Fork Locally [02:48:37]:
    Bash 
    git clone git@github.com:your-username/repository-name.git
cd repository-name
  3. Keep Fork Synced with Upstream:
    Bash 
    git remote add upstream git@github.com:original-owner/repository-name.git
git fetch upstream
git merge upstream/main
  4. Create a Descriptive Feature Branch:
    Bash 
    git switch -c fix-navbar-overflow
  5. Implement Changes, Test, Stage & Commit:
    Bash 
    git add .
git commit -m "Fix navbar overflow on mobile screen widths"
  6. Push Feature Branch to Your Remote Fork [02:49:58]:
    Bash 
    git push -u origin fix-navbar-overflow
  7. Open a Pull Request (PR) on GitHub [02:50:53]:

    Go to your repository on GitHub. Click Compare & pull request. Provide a clear title, description of changes, and reference any solved issues (e.g., Closes #42).
