Module 1: Foundations of Databases & PostgreSQL Architecture

1.1 What is a Database?

A Database is an organized, structured collection of data stored electronically, paired with systematic methods to access, manipulate, and manage that data. Consider an physical analogy: finding a specific science book in a chaotic pile of millions of unorganized books is virtually impossible. However, in a structured library categorized by subject, index, author, and shelf position, retrieval takes seconds. Databases enforce this structured categorization electronically.

1.2 Why Use a Relational Database Instead of Excel / Spreadsheets?

While Microsoft Excel or spreadsheets present data in rows and columns, they fail catastrophically when scaled for enterprise applications:

  • Scalability & Performance: Spreadsheets crash or freeze when handling millions of rows. Relational databases easily index and manage billions of rows with sub-second response times.
  • Concurrent Access: Spreadsheets suffer file-locking issues when multiple users or web apps read/write simultaneously. Databases support thousands of concurrent transactions via Multi-Version Concurrency Control (MVCC).
  • Data Integrity & ACID Compliance: Databases enforce strict constraint rules (foreign keys, check constraints) ensuring invalid data cannot corrupt the system.
  • Security & Granular Permissions: Databases restrict access down to specific columns, rows, or schemas.

1.3 DBMS vs. RDBMS

  • DBMS (Database Management System): Software acting as a bridge between user applications and physical data storage (e.g., file systems, key-value stores).
  • RDBMS (Relational Database Management System): A specialized subset of DBMS that stores data strictly in two-dimensional structured tables (rows and columns) using SQL (Structured Query Language) to establish mathematical relations between tables via primary and foreign keys.

1.4 Database Engine Landscape & Why Choose PostgreSQL?

Common database engines include PostgreSQL, MySQL, Oracle, MongoDB (NoSQL document store), Redis (in-memory key-value), MariaDB, and SQLite. PostgreSQL is widely recognized as the world's most advanced open-source relational database due to its:

  • Full ACID (Atomicity, Consistency, Isolation, Durability) compliance out-of-the-box.
  • Extensible architecture supporting rich native data types (JSONB, Arrays, UUID, PostGIS spatial data).
  • High enterprise industry demand in backend architecture, fintech, data analytics, and AI/ML ecosystems.

1.5 SQL vs. PostgreSQL

SQL (Structured Query Language) is the standardized declarative language used to query databases. PostgreSQL is the actual database management software tool that implements SQL alongside advanced procedural extensions (PL/pgSQL).

Module 2: Installation, Client Interfaces & System Architecture

2.1 Default Installation Configuration Parameters

Regardless of operating system (Windows, macOS, Linux/CentOS/Ubuntu), standard PostgreSQL setups initialize with:

  • Default Superuser Account: postgres
  • Default Listening Port: 5432
  • Default Initial Database: postgres

2.2 PostgreSQL Client Tools: pgAdmin 4 vs. psql CLI

  • pgAdmin 4: Web/Desktop Graphical User Interface (GUI) dashboard for schema visualization, query execution, server performance monitoring, and graphical database administration.
  • psql (SQL Shell): Powerful interactive Command Line Interface (CLI) tool preferred by developers and DBAs for scripting, fast query execution, and remote server management.
Environment Variable Configuration (Windows/Linux/macOS)

To execute psql directly from any system terminal, append the PostgreSQL installation binary path (e.g., C:\Program Files\PostgreSQL\<version>\bin) to system Environment Variables (PATH).

2.3 Essential psql Meta-Commands Cheat Sheet

psql meta-commands begin with a backslash (\) and operate independently of SQL semi-colon rules:

Meta-Command Description / Purpose Example Usage

\dt Lists all tables in the active schema (defaults to public). \dt
\d <table> Describes schema breakdown (columns, types, modifiers, indexes, FKs). \d employee

Module 3: Database & Table Management + Core CRUD Operations

3.1 Database Management Syntax

sql 
-- Create a new database
CREATE DATABASE person_db;

-- List existing databases via System Catalog Query
SELECT datname FROM pg_database;

-- Drop (Delete) a database (Must disconnect active sessions first)
DROP DATABASE person_db;

3.2 Table Creation Syntax & Conventions

SQL syntax is case-insensitive (e.g., CREATE TABLE vs create table), but industry standard practice dictates using UPPERCASE for SQL keywords and lowercase for table/column identifiers.

sql 
CREATE TABLE person (
    id INT,
    name VARCHAR(100),
    city VARCHAR(100)
);

3.3 The 4 Core CRUD Operations

CRUD represents the fundamental data operations: Create, Read, Update, and Delete.

sql 
-- 1. CREATE (Insert Records)
-- Single record insertion specifying target columns
INSERT INTO person (id, name, city) VALUES (101, 'Raju', 'Delhi');

-- Multi-row bulk insertion
INSERT INTO person (id, name, city) VALUES 
(102, 'Shyam', 'Mumbai'),
(103, 'Paul', 'Chennai');

-- Positional insertion (omitting column list requires providing ALL values in exact schema order)
INSERT INTO person VALUES (104, 'Alex', 'Pune');

-- 2. READ (Query Records)
-- Fetch all columns and rows
SELECT * FROM person;

-- Projection: Fetch specific columns only
SELECT name, city FROM person;

-- 3. UPDATE (Modify Existing Records)
-- CRITICAL: Always pair UPDATE with a WHERE clause to target specific rows
UPDATE person 
SET city = 'Bangalore' 
WHERE name = 'Raju';

-- 4. DELETE (Remove Records)
-- Delete specific row based on condition
DELETE FROM person 
WHERE id = 104;

Module 4: Deep Dive into Data Types & Integrity Constraints

WARNING — The Unbounded Update/Delete Pitfall

Executing UPDATE person SET city = 'Bangalore'; or DELETE FROM person; without a WHERE clause will modify or wipe out EVERY SINGLE ROW in the table! Always test filtering logic with SELECT before executing mutation commands.

4.2 Data Integrity Constraints Explained

  • PRIMARY KEY: Uniquely identifies each record in a table. Internally enforces both UNIQUE and NOT NULL, automatically building a B-tree index. A table can possess only one Primary Key.
  • NOT NULL: Prevents columns from storing empty/missing NULL values.
  • UNIQUE: Ensures every entry in a column is distinct across all rows. (Unlike Primary Keys, allows storing NULL unless paired with NOT NULL).
  • DEFAULT: Assigns an automatic baseline value if no value is explicitly supplied during insertion (e.g., DEFAULT 30000.00 or dynamic server functions like DEFAULT CURRENT_DATE).
  • CHECK: Enforces boolean expressions to validate inputs before insertion/update (e.g., CHECK (age >= 18)).

4.3 Mechanics of Auto-Increment Sequences (SERIAL)

When a column is declared as SERIAL, PostgreSQL automatically executes three background tasks:

  1. Creates a sequence object named <table>_<column>_seq.
  2. Sets column default to nextval('sequence_name').
  3. Assigns sequence ownership to the table column.

Handling Sequence Desynchronization / Primary Key Collisions

If manual numeric insertions occur on a SERIAL column (e.g. explicitly forcing emp_id = 1), the background sequence pointer does not auto-advance. Subsequent automated inserts will trigger a duplicate key error! Fix this by inspecting sequence state and resetting pointer offset:

sql 
-- Inspect current sequence value
SELECT currval('employee_emp_id_seq');

-- Set sequence counter to match max existing primary key ID
SELECT setval('employee_emp_id_seq', (SELECT MAX(emp_id) FROM employee));

Module 5: SQL Clauses, Filtering & Logical Operators

5.1 Comparison & Logical Operators

sql 
-- Exact Match
SELECT * FROM employee WHERE emp_id = 5;

-- Relational Filtering (Salary >= 50,000)
SELECT * FROM employee WHERE salary >= 50000.00;

-- Logical AND (Both conditions must be TRUE)
SELECT * FROM employee WHERE department = 'IT' AND salary > 50000.00;

-- Logical OR (Either condition TRUE)
SELECT * FROM employee WHERE department = 'HR' OR department = 'Finance';

5.2 Set Matching (IN) & Range Search (BETWEEN)

sql 
-- Replacing repetitive OR conditions using IN
SELECT * FROM employee WHERE department IN ('IT', 'Finance', 'HR');

-- Negation: Exclude specific departments
SELECT * FROM employee WHERE department NOT IN ('Marketing');

-- Inclusive Range Search using BETWEEN
SELECT * FROM employee WHERE salary BETWEEN 40000.00 AND 60000.00;

5.3 Result Presentation: Distinct, Sorting & Pagination

sql 
-- Extract distinct unique values from a column
SELECT DISTINCT department FROM employee;

-- Sort records ascending (Default)
SELECT * FROM employee ORDER BY first_name ASC;

-- Sort records descending by salary
SELECT * FROM employee ORDER BY salary DESC;

-- Pagination: Limit output to top 3 highest earners
SELECT * FROM employee ORDER BY salary DESC LIMIT 3 OFFSET 0;

5.4 Pattern Matching Wildcards (LIKE & ILIKE)

The LIKE operator performs case-sensitive pattern matching, whereas ILIKE is PostgreSQL's case-insensitive extension.

  • % Wildcard: Matches zero, one, or multiple characters.
  • _ Wildcard: Matches exactly one character.
sql 
-- Names starting with 'A'
SELECT * FROM employee WHERE first_name LIKE 'A%';

-- Names ending with 'a'
SELECT * FROM employee WHERE first_name LIKE '%a';

-- Names containing letter 'i' anywhere
SELECT * FROM employee WHERE first_name LIKE '%i%';

-- Names where the SECOND character is exactly 'a' (e.g., Raj, Rahul)
SELECT * FROM employee WHERE first_name LIKE '_a%';

-- Names containing exactly 4 characters (4 underscores)
SELECT * FROM employee WHERE first_name LIKE '____';

-- Filter departments having exactly 2 characters (e.g., IT, HR)
SELECT * FROM employee WHERE department LIKE '__';

Module 6: Aggregate Functions & Categorical Grouping Mechanics

6.1 Standard Aggregate Functions

sql 
-- Total employee headcount
SELECT COUNT(emp_id) AS total_employees FROM employee;

-- Cumulative total payroll budget
SELECT SUM(salary) AS total_payroll FROM employee;

-- Average organization salary
SELECT AVG(salary) AS average_salary FROM employee;

-- Salary boundary extremes
SELECT MIN(salary) AS lowest_salary, MAX(salary) AS highest_salary FROM employee;

6.2 Categorical Grouping (GROUP BY)

The GROUP BY clause categorizes individual table rows into distinct summary buckets based on common values in specified columns.

Golden Rule of GROUP BY

Any non-aggregated column present in the SELECT projection list MUST be explicitly included in the GROUP BY clause!

sql 
-- Count headcount per department
SELECT department, COUNT(emp_id) AS headcount 
FROM employee 
GROUP BY department;

-- Total payroll expense per department
SELECT department, SUM(salary) AS department_payroll 
FROM employee 
GROUP BY department;

-- Departmental salary averages and max earner bounds
SELECT department, AVG(salary) AS avg_sal, MAX(salary) AS max_sal 
FROM employee 
GROUP BY department;

Module 7: PostgreSQL String Manipulation Functions & Workshop

7.1 Native String Function Suite

Function Description Example & Output
CONCAT(s1, s2) Combines strings together; treats NULL as empty string. CONCAT('Hello', 'World') → 'HelloWorld'
CONCAT_WS(sep, s1, s2) Concatenates strings With Separator as first argument. CONCAT_WS('-', '101', 'Raj', 'IT') → '101-Raj-IT'
SUBSTRING(s FROM p FOR l) Extracts text substring starting at position p for length l. SUBSTRING('Hello World' FROM 1 FOR 5) → 'Hello'

Module 8: Schema Alterations (ALTER TABLE) & Advanced Constraints

8.1 Table Schema Mutation Syntax

sql 
-- Add a new column with default value
ALTER TABLE person ADD COLUMN age INT DEFAULT 0;

-- Drop an existing column
ALTER TABLE person DROP COLUMN age;

-- Rename a column identifier
ALTER TABLE person RENAME COLUMN name TO first_name;

-- Modify data type and expand size capacity
ALTER TABLE person ALTER COLUMN first_name SET DATA TYPE VARCHAR(150);

-- Add / Drop NOT NULL constraint
ALTER TABLE person ALTER COLUMN first_name SET NOT NULL;
ALTER TABLE person ALTER COLUMN first_name DROP NOT NULL;

-- Set / Drop DEFAULT values
ALTER TABLE person ALTER COLUMN city SET DEFAULT 'Unknown';
ALTER TABLE person ALTER COLUMN city DROP DEFAULT;

8.2 Table Validation Rules via CHECK Constraints

CHECK constraints evaluate expressions on insertion/update. Explicitly naming constraints using CONSTRAINT <name> ensures readable database logs when validations fail.

sql 
-- Add mobile column
ALTER TABLE person ADD COLUMN mobile VARCHAR(15);

-- Add explicit named CHECK constraint enforcing mobile length >= 10
ALTER TABLE person 
ADD CONSTRAINT mobile_num_min_10_digits 
CHECK (LENGTH(mobile) >= 10);

-- Testing validation failure (Triggers error: "mobile_num_min_10_digits" violated)
-- INSERT INTO person (first_name, mobile) VALUES ('Test', '123');

-- Drop named constraint
ALTER TABLE person DROP CONSTRAINT mobile_num_min_10_digits;

Module 9: Conditional Logic with CASE WHEN Expressions

9.1 CASE WHEN Syntax & Multi-Tier Classification

sql 
SELECT first_name, salary,
    CASE 
        WHEN salary >= 55000.00 THEN 'High Salary'
        WHEN salary BETWEEN 48000.00 AND 54999.99 THEN 'Mid Salary'
        ELSE 'Low Salary'
    END AS salary_tier
FROM employee;

9.2 Mathematical Operations & Bonus Calculations

sql 
-- Calculate 10% annual bonus rounded to 2 decimal places
SELECT first_name, salary,
    ROUND(
        CASE 
            WHEN salary > 0 THEN salary * 0.10
            ELSE 0
        END, 2
    ) AS annual_bonus
FROM employee;

9.3 Combining CASE Expressions with GROUP BY Aggregations

sql 
SELECT 
    CASE 
        WHEN salary >= 55000.00 THEN 'High Tier'
        WHEN salary BETWEEN 48000.00 AND 54999.99 THEN 'Mid Tier'
        ELSE 'Low Tier'
    END AS tier_category,
    COUNT(emp_id) AS total_employees
FROM employee
GROUP BY 
    CASE 
        WHEN salary >= 55000.00 THEN 'High Tier'
        WHEN salary BETWEEN 48000.00 AND 54999.99 THEN 'Mid Tier'
        ELSE 'Low Tier'
    END;

Module 10: Relational Architecture & Foreign Key Mechanics

10.1 Relational Normalization & Table Cardinality

  • One-to-One (1:1): Each row in Table A corresponds strictly to one row in Table B (e.g. Employee ↔ Passport Details).
  • One-to-Many (1:N): One row in Table A associates with multiple rows in Table B (e.g. One Customer ↔ Multiple Orders; One Department ↔ Multiple Employees). Most common architectural relationship.
  • Many-to-Many (N:M): Multiple records in Table A map to multiple records in Table B (e.g. Students ↔ Courses; Authors ↔ Books). Implemented physically via an intermediary Junction / Associative Table containing composite foreign keys.

10.2 Foreign Key Mechanics & Referencing Rules

A Foreign Key is a column in a child table referencing the Primary Key of a parent table. Foreign keys enforce referential integrity: records cannot be inserted into a child table referencing a non-existent parent ID.

sql 
-- Parent Table: Customers
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL
);

-- Child Table: Orders (Contains Foreign Key)
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    order_date DATE DEFAULT CURRENT_DATE,
    price DECIMAL(10, 2),
    customer_id INT,
    CONSTRAINT fk_customer 
        FOREIGN KEY (customer_id) 
        REFERENCES customers(customer_id)
);

-- Populate Data
INSERT INTO customers (customer_name, email) VALUES 
('Raju', 'raju@gmail.com'),
('Shyam', 'shyam@gmail.com'),
('Paul', 'paul@gmail.com');

INSERT INTO orders (order_date, price, customer_id) VALUES 
('2024-01-10', 250.00, 1),
('2024-01-12', 300.00, 1),
('2024-01-15', 700.00, 2);

Module 11: SQL Joins — Multi-Table Data Retrieval

11.1 Relational Join Types Overview

  • CROSS JOIN: Returns Cartesian product (combines every row of Left table with every row of Right table).
  • INNER JOIN: Returns ONLY records where join predicate condition matches in BOTH tables.
  • LEFT JOIN (LEFT OUTER JOIN): Returns ALL rows from the Left table + matching records from the Right table (unmatched right side columns render as NULL).
  • RIGHT JOIN (RIGHT OUTER JOIN): Returns ALL rows from the Right table + matching records from the Left table.
sql 
-- INNER JOIN: Fetch orders paired with customer details (Excludes customers without orders)
SELECT c.customer_name, o.order_id, o.order_date, o.price
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;

-- LEFT JOIN: Fetch ALL customers including those who have placed ZERO orders
SELECT c.customer_name, o.order_id, o.price
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

-- JOIN WITH AGGREGATION: Total customer spend
SELECT c.customer_name, COUNT(o.order_id) AS total_orders, SUM(o.price) AS total_spent
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_name;

11.2 Many-to-Many Relationship Implementation (3-Table Join)

sql 
-- Primary Table 1: Students
CREATE TABLE students (
    student_id SERIAL PRIMARY KEY,
    student_name VARCHAR(100) NOT NULL
);

-- Primary Table 2: Courses
CREATE TABLE courses (
    course_id SERIAL PRIMARY KEY,
    course_name VARCHAR(100) NOT NULL,
    fee DECIMAL(10, 2)
);

-- Intermediary Junction Table: Enrollments
CREATE TABLE enrollments (
    enrollment_id SERIAL PRIMARY KEY,
    student_id INT REFERENCES students(student_id),
    course_id INT REFERENCES courses(course_id),
    enroll_date DATE DEFAULT CURRENT_DATE
);

-- Seed Junction Data
INSERT INTO students (student_name) VALUES ('Raju'), ('Shyam'), ('Alex');
INSERT INTO courses (course_name, fee) VALUES ('Maths', 500.00), ('Physics', 600.00);
INSERT INTO enrollments (student_id, course_id) VALUES (1, 1), (1, 2), (2, 1);

-- 3-TABLE JOIN QUERY: Fetch Student Names, Enrolled Course Names & Fees
SELECT s.student_name, c.course_name, c.fee, e.enroll_date
FROM enrollments e
JOIN students s ON e.student_id = s.student_id
JOIN courses c ON e.course_id = c.course_id;

Module 12: End-to-End E-Commerce Store Project

This hands-on architecture combines 1:N and N:M relationships across 4 core enterprise tables: store_customers, store_orders, store_products, and order_items.

sql 
-- 1. Create E-Commerce Tables
CREATE TABLE store_customers (
    cust_id SERIAL PRIMARY KEY,
    cust_name VARCHAR(100) NOT NULL
);

CREATE TABLE store_orders (
    order_id SERIAL PRIMARY KEY,
    order_date DATE DEFAULT CURRENT_DATE,
    cust_id INT REFERENCES store_customers(cust_id)
);

CREATE TABLE store_products (
    product_id SERIAL PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    unit_price DECIMAL(10, 2) NOT NULL
);

CREATE TABLE order_items (
    item_id SERIAL PRIMARY KEY,
    order_id INT REFERENCES store_orders(order_id),
    product_id INT REFERENCES store_products(product_id),
    quantity INT NOT NULL DEFAULT 1
);

-- 2. Seed E-Commerce Data
INSERT INTO store_customers (cust_name) VALUES ('Raju'), ('Shyam'), ('Paul');
INSERT INTO store_orders (cust_id) VALUES (1), (2); -- Order 1 (Raju), Order 2 (Shyam)
INSERT INTO store_products (product_name, unit_price) VALUES 
('Laptop', 55000.00), ('Mouse', 500.00), ('Keyboard', 800.00);
INSERT INTO order_items (order_id, product_id, quantity) VALUES 
(1, 1, 1), -- Raju bought 1 Laptop
(1, 2, 2), -- Raju bought 2 Mice
(2, 3, 1); -- Shyam bought 1 Keyboard

-- 3. Master 4-Table Analytical Billing Query
SELECT 
    c.cust_name,
    o.order_id,
    o.order_date,
    p.product_name,
    p.unit_price,
    oi.quantity,
    (oi.quantity * p.unit_price) AS line_item_total
FROM order_items oi
JOIN store_orders o ON oi.order_id = o.order_id
JOIN store_customers c ON o.cust_id = c.cust_id
JOIN store_products p ON oi.product_id = p.product_id;

Module 13: Database Views, HAVING Clause & Subtotals

13.1 Database Views (CREATE VIEW)

A View is a saved virtual table encapsulating complex multi-table joins. Views do NOT duplicate underlying data; they dynamically execute stored query logic upon access.

sql 
-- Encapsulate complex e-commerce join query into a View
CREATE VIEW billing_info_view AS
SELECT 
    c.cust_name, o.order_id, p.product_name, p.unit_price, oi.quantity,
    (oi.quantity * p.unit_price) AS line_item_total
FROM order_items oi
JOIN store_orders o ON oi.order_id = o.order_id
JOIN store_customers c ON o.cust_id = c.cust_id
JOIN store_products p ON oi.product_id = p.product_id;

-- Query Virtual View cleanly as a normal table
SELECT * FROM billing_info_view WHERE line_item_total > 1000.00;

13.2 The HAVING Clause vs. WHERE Clause

Key Distinction:

  • WHERE filters individual raw rows BEFORE aggregation occurs.
  • HAVING filters categorical group summary rows AFTER GROUP BY calculations complete.

Note: Attempting WHERE SUM(sales) > 1000 triggers a SQL compilation syntax error! Use HAVING instead.

sql 
-- Find product categories generating total revenue exceeding $1,000
SELECT product_name, SUM(line_item_total) AS total_revenue
FROM billing_info_view
GROUP BY product_name
HAVING SUM(line_item_total) > 1000.00;

13.3 Hierarchical Subtotals with ROLLUP

sql 
-- ROLLUP auto-generates subtotal and grand total summary rows
-- COALESCE replaces NULL headers in summary rows with 'GRAND TOTAL'
SELECT 
    COALESCE(product_name, 'GRAND TOTAL') AS product_label,
    SUM(line_item_total) AS revenue
FROM billing_info_view
GROUP BY ROLLUP(product_name);

Module 14: Stored Routines — Stored Procedures & User Defined Functions

14.1 Stored Procedures (CREATE PROCEDURE)

Stored Procedures contain precompiled procedural SQL statements stored on the database server. They execute action operations (INSERT, UPDATE, DELETE) and are invoked using the CALL statement.

sql 
-- Create Procedure to update employee salary safely
CREATE OR REPLACE PROCEDURE update_emp_salary(
    p_emp_id INT,
    p_new_salary DECIMAL(10, 2)
)
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE employee 
    SET salary = p_new_salary 
    WHERE emp_id = p_emp_id;
END;
$$;

-- Invoke Procedure using CALL
CALL update_emp_salary(3, 71000.00);

14.2 User Defined Functions (UDFs)

User Defined Functions (UDFs) compute values or return dynamic result tables. Unlike Procedures, Functions are called inline directly inside SELECT statements.

sql 
-- Create Function returning a result table of top earners for a given department
CREATE OR REPLACE FUNCTION get_dept_max_earner(p_dept_name VARCHAR)
RETURNS TABLE(r_emp_id INT, r_first_name VARCHAR, r_salary DECIMAL)
LANGUAGE plpgsql
AS $$
BEGIN
    RETURN QUERY
    SELECT emp_id, first_name, salary
    FROM employee
    WHERE department = p_dept_name
      AND salary = (SELECT MAX(salary) FROM employee WHERE department = p_dept_name);
END;
$$;

-- Query Function inline via SELECT
SELECT * FROM get_dept_max_earner('IT');

Module 15: Window Functions & Analytical SQL

15.1 What are Window Functions?

Window Functions perform calculations across sets of related table rows (a "window") WITHOUT collapsing individual rows into single summary lines (unlike GROUP BY). Every original row retains its identity while displaying calculated window values.

15.2 The OVER() Clause Mechanics: Running Totals & Averages

sql 
-- Calculate Running Cumulative Salary Total ordered by salary ASC
SELECT first_name, salary,
    SUM(salary) OVER(ORDER BY salary ASC) AS running_total,
    AVG(salary) OVER(ORDER BY salary ASC) AS running_avg
FROM employee;

15.3 Window Ranking Functions: ROW_NUMBER, RANK, and DENSE_RANK

  • ROW_NUMBER(): Assigns a unique sequential integer counter to every row.
  • RANK(): Assigns rank; leaves gaps when ties occur (e.g. 1, 1, 3).
  • DENSE_RANK(): Assigns rank; leaves NO gaps when ties occur (e.g. 1, 1, 2).
sql 
-- Ranking Employees Organization-Wide by Salary
SELECT first_name, salary,
    ROW_NUMBER() OVER(ORDER BY salary DESC) AS row_num,
    RANK() OVER(ORDER BY salary DESC) AS rank_with_gaps,
    DENSE_RANK() OVER(ORDER BY salary DESC) AS dense_rank_no_gaps
FROM employee;

-- Partitioned Ranking: Rank Employees WITHIN EACH DEPARTMENT independently
SELECT first_name, department, salary,
    DENSE_RANK() OVER(PARTITION BY department ORDER BY salary DESC) AS dept_rank
FROM employee;

15.4 Offset Window Functions: LAG, LEAD & Delta Metrics

sql 
-- Compare employee salary against the salary of the next higher earner (LEAD)
SELECT first_name, salary,
    LEAD(salary) OVER(ORDER BY salary DESC) AS next_higher_salary,
    (salary - LEAD(salary) OVER(ORDER BY salary DESC)) AS salary_delta
FROM employee;

Module 16: Common Table Expressions (CTEs) — The WITH Clause

16.1 What is a Common Table Expression (CTE)?

A CTE (Common Table Expression) is a temporary named result set defined using the WITH keyword. CTEs modularize complex multi-stage analytical queries, serving as a clean alternative to deeply nested inline subqueries. A CTE exists only during execution of the main query.

sql 
-- Define CTE calculating departmental average salaries
WITH dept_avg_cte AS (
    SELECT department, AVG(salary) AS avg_dept_salary
    FROM employee
    GROUP BY department
)
-- Main Query joining employee table with CTE result set
SELECT e.first_name, e.department, e.salary, ROUND(d.avg_dept_salary, 2) AS dept_avg
FROM employee e
JOIN dept_avg_cte d ON e.department = d.department
WHERE e.salary > d.avg_dept_salary;

Module 17: Database Triggers & Master Cheat Sheet

17.1 What is a Database Trigger?

A Trigger is an event-driven callback procedure automatically executed by PostgreSQL whenever a specified mutation event (BEFORE or AFTER INSERT, UPDATE, or DELETE) occurs on a target table.

sql 
-- 1. Create Trigger Function enforcing non-negative salaries
CREATE OR REPLACE FUNCTION sanitize_salary_func()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    -- Intercept attempted negative salary updates and automatically reset to 0.00
    IF NEW.salary < 0 THEN
        NEW.salary := 0.00;
    END IF;
    RETURN NEW;
END;
$$;

-- 2. Bind Trigger to Employee Table
CREATE TRIGGER trg_sanitize_salary
BEFORE INSERT OR UPDATE ON employee
FOR EACH ROW
EXECUTE FUNCTION sanitize_salary_func();

-- Test Trigger Execution
UPDATE employee SET salary = -50000.00 WHERE emp_id = 1;

-- Verification Query: Salary for emp_id 1 is automatically reset to 0.00!
SELECT emp_id, first_name, salary FROM employee WHERE emp_id = 1;
